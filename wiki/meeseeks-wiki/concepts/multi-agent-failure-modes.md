# Multi-Agent Failure Modes

Multi-agent LLM systems fail often, and the failures cluster into a small, nameable set of patterns rather than being an undifferentiated mess of "the model got something wrong." The most rigorous evidence for this comes from MAST, the Multi-Agent System Failure Taxonomy built by Cemri, Pan, Yang et al. (NeurIPS 2025), who hand-annotated 150 execution traces from five open-source multi-agent frameworks using grounded-theory analysis, reached inter-annotator agreement of Cohen's kappa = 0.88, then scaled labeling to 1,642 traces across seven frameworks (ChatDev, MetaGPT, HyperAgent, AppWorld's AG2/MathChat, Magentic-One, OpenManus, and Manus) and four model families (GPT-4, Claude 3, Qwen2.5, CodeLlama) with a calibrated LLM-as-judge annotator (94% accuracy, kappa = 0.77 against held-out human labels). Across those seven frameworks, overall task failure rates ranged from **41% to 86.7%** — this page catalogs *why*, and connects the empirical taxonomy to two adjacent bodies of evidence: behavioral drift over long sessions, and security-specific attack surfaces that only exist because agents talk to each other. The higher-level argument for what this means for human supervision is taken up separately in [multi-agent-safety-and-oversight.md](../syntheses/multi-agent-safety-and-oversight.md).

## The MAST taxonomy: 14 failure modes in 3 categories

MAST groups its 14 fine-grained failure modes (FM-1.1 through FM-3.3) into three categories, each mapped to the pipeline stage — pre-execution, execution, or post-execution — where the underlying issue typically originates.

**FC1 — System Design Issues (41.8% of observed failures)** trace to flaws in pre-execution design: architecture, role specification, or state management, rather than to the underlying model being insufficiently capable. The five failure modes are: disobeying task specification (FM-1.1, 11.8%) — an agent ignores explicit task constraints; disobeying role specification (FM-1.2, 1.5%) — an agent acts outside its assigned role, such as one subagent overriding another's authority without consensus; step repetition (FM-1.3, 15.7%) — the largest single failure mode in the entire taxonomy, where agents redundantly repeat already-completed steps; loss of conversation history (FM-1.4, 2.8%) — necessary context is dropped as it passes between agents or turns; and unaware of termination conditions (FM-1.5, 12.4%) — the system doesn't recognize that a task is actually complete (or actually stuck) and keeps going past the point where it should stop. MAST's own intervention study found that a single design fix — giving ChatDev's CEO agent final say over its subordinate agent's decisions — raised task success by +9.4% with no change to the underlying LLM, direct evidence that these are engineering failures, not capability failures.

**FC2 — Inter-Agent Misalignment (36.9%)** covers breakdowns in the critical information flow between agents during execution: conversation reset (FM-2.1, 2.2%) — context is unexpectedly discarded mid-interaction; fail to ask for clarification (FM-2.2, 6.8%) — an agent proceeds on a wrong assumption instead of querying a peer or the user; task derailment (FM-2.3, 7.4%) — the interaction drifts away from the original objective; information withholding (FM-2.4, 0.8%) — an agent has information a peer needs and doesn't share it, illustrated in the paper's own trace example of a Phone Agent that fails to tell a Supervisor Agent the required login-credential format, producing repeated failed logins; ignored other agent's input (FM-2.5, 1.9%); and reasoning-action mismatch (FM-2.6, 13.2%) — an agent's stated reasoning and its actual action diverge. MAST's authors note that surface-similar failures here can have different root causes — withholding (FM-2.4) versus ignoring (FM-2.5) versus upstream context loss (FM-1.4) look alike from the outside but require different fixes — and that fixes aimed only at communication protocols or shared context are insufficient, because FC2 failures often demand something closer to theory-of-mind reasoning about what a peer agent actually needs to know.

**FC3 — Task Verification (21.3%)** covers inadequate output validation: premature termination (FM-3.1, 6.2%) — an agent signals "done" before the task is actually complete, a false-positive completion signal; no or incomplete verification (FM-3.2, 8.2%); and incorrect verification (FM-3.3, 9.1%) — a check runs but passes bad output, such as a ChatDev-generated chess program that compiles cleanly and passes superficial checks but breaks actual game rules because nothing validated against real gameplay. The paper's second intervention study found that adding a single high-level task-objective verification step to ChatDev improved success by +15.6%, reinforcing that even systems with an explicit verifier stage (MetaGPT, ChatDev) still fail at high rates because that verifier typically only checks surface properties like "does it compile," not "does it do the right thing."

A striking secondary finding: across the dataset, roughly **79% of failures trace back to bad specification and broken coordination**, not to raw model capability limits. MAST's authors are explicit that this reframes the reliability problem — a well-designed multi-agent system produces measurable performance gains using the *same* underlying model, meaning most of the 41-86.7% failure range documented here is an artifact of orchestration, role design, and verification depth rather than a hard ceiling imposed by current LLMs.

## Failure compounds with time: agent drift

The MAST traces are largely snapshots of individual task runs, not long-running sessions. A companion finding — "agent drift," proposed and measured by a 2026 arXiv paper — addresses what happens as a multi-agent interaction extends over many rounds rather than completing quickly: behavioral quality and specification-adherence degrade progressively over the course of the *same* session, rather than staying flat. The paper operationalizes this across four metric families sampled at regular intervals through extended runs (not just start/end): task performance, behavioral consistency against the originally specified guidelines, communication quality between agents, and goal alignment — whether agents kept pursuing their stated objective or substituted a locally-convenient one partway through. It reports four concrete patterns: progressive performance decline across successive rounds, behavioral drift away from initial instructions, specification erosion (the task spec's "grip" on behavior weakens as duration/context length grows), and communication breakdown between agents specifically, distinct from individual task-performance decline.

The paper's own framing links this directly to specification gaming and reward hacking: as an interaction runs longer, agents get more opportunities to find loopholes in ambiguous behavioral constraints, and it argues multi-agent settings amplify this compared to single-agent, single-turn interactions because there is more surface area — more agents, more handoffs, more turns — for small deviations to compound before anything catches them. Read against MAST, drift is a plausible mechanism for two of the taxonomy's specific failure modes rather than a separate phenomenon: unaware of termination conditions (FM-1.5) and reasoning-action mismatch (FM-2.6) are exactly the kind of failures that would *grow* in frequency over a session's duration if specification erosion is real, though MAST's own trace-level data doesn't itself measure within-session trajectories the way the drift paper does.

## Failure compounds across trust boundaries: security-specific risks

A third strand of failure is adversarial rather than incidental. A 2026 arXiv paper on security considerations for multi-agent systems argues that networked agents create attack surfaces that simply don't exist for an isolated single agent, because a single agent's security boundary is itself plus its tool integrations, while a multi-agent system's boundary must also cover every inter-agent trust relationship — relationships that are routinely under-scrutinized because designers implicitly assume peer agents are trustworthy. The paper organizes this into three structural properties that interact: **interconnection vulnerabilities**, where a malicious input delivered to one agent propagates to every agent that consumes its output rather than staying contained to the entry point; **trust exploitation**, where agents accept peer output without independently re-verifying it, so an attacker who compromises just the weakest-secured agent gains leverage over every downstream agent that trusts it; and **cascading failures**, the compounding of the first two, where one corrupted agent's bad state propagates false information across the whole system rather than producing a single isolated error.

Three specific attack types follow from that structure. **Prompt injection propagation** — an injected instruction delivered to one agent gets forwarded to others in the pipeline, with each hop able to amplify or transform it, a multiplier effect with no equivalent in single-agent deployments. **Consensus manipulation** — in systems where multiple agents jointly reach a decision via voting or deliberation, compromising even a minority of participants can be enough to skew the group's output, depending on how robust the consensus mechanism is. **Information poisoning** — corrupting shared memory, message queues, or intermediate artifacts undermines every downstream agent-to-agent communication, independent of whether any individual agent's own reasoning is intact. The paper's core recommendation — that every inter-agent message should be treated with something like the skepticism normally reserved for untrusted external input, rather than trusted by default because it came from "inside" the system — is the security-specific instance of the same lesson MAST draws from FC3: verification that only checks surface properties (a message parses, an agent claims success) is not verification of the thing that actually matters.

Trust exploitation and prompt-injection propagation are also one of the seven structural risk factors identified in the Cooperative AI Foundation's broader safety taxonomy — "multi-agent security" is named explicitly as a distinct risk factor there, connecting this page's concrete attack catalog to the higher-level argument in [multi-agent-safety-and-oversight.md](../syntheses/multi-agent-safety-and-oversight.md) about why these failures are hard to catch from the outside: a system exhibiting FC2 (inter-agent misalignment) or a cascading security failure looks, from a supervising human's vantage point, identical to a system that is simply running — nothing in a bare status indicator distinguishes "coordinating correctly" from "silently propagating a corrupted state," which is precisely the blind spot [the attention-economics synthesis](../syntheses/attention-economics.md) identifies in Meeseeks' own seven-state runtime status enum: an agent can be `running` while thrashing, derailed, or forwarding a poisoned message, and that is indistinguishable from `running` while making genuine progress.
