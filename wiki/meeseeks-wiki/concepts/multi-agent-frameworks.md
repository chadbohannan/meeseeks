# Multi-Agent Frameworks: Architectural Philosophies

Multi-agent frameworks split into a small number of recurring architectural philosophies about how independent LLM-backed agents should coordinate: peer-to-peer dynamic handoff, conversation-driven orchestration with configurable topology, role-based teams that can run either autonomously or deterministically, fixed-role assembly-line pipelines, and — at a different layer entirely — cross-vendor interoperability protocols that let agents built on *different* frameworks talk to each other. This page surveys eight frameworks/protocols against that taxonomy: OpenAI Swarm, CAMEL, AutoGen/AG2, CrewAI, MetaGPT, ChatDev, and Google's A2A. It complements the [attention economics synthesis](../syntheses/attention-economics.md) and the [harness-paradigms comparison](../syntheses/harness-paradigms.md) by focusing specifically on *inter-agent* coordination rather than single-agent tool loops.

## Peer-to-peer, dynamic handoff: OpenAI Swarm and CAMEL

OpenAI Swarm and CAMEL both reject a central orchestrator process in favor of control flow that emerges from the agents' own interactions, but they arrive at that shape from opposite directions — Swarm via explicit function-call handoffs, CAMEL via a scripted two-role dialogue.

Swarm, described in its own README as "an educational framework exploring ergonomic, lightweight multi-agent orchestration," builds on OpenAI's stateless Chat Completions API rather than the server-side-stateful Assistants API, and runs "almost entirely on the client." Its two core abstractions are the **Agent** — a bundle of instructions (a static string or a function that generates the prompt from context) plus a set of Python functions — and the **Handoff**: any function an agent calls can return another `Agent` object instead of a normal value, which transfers control of the conversation to that agent. The README frames this explicitly as enabling "flexible workflows rather than rigid hierarchies," since the handoff graph emerges from whichever functions get invoked rather than from a fixed org chart. A `Result` object lets a single function call simultaneously return a value, trigger a handoff, and update a plain-dictionary **context variables** store threaded through the whole run, and `client.run()` executes a simple imperative loop — get a completion, execute any tool calls, switch agent on handoff, merge context updates, repeat until no new calls remain — rather than a hidden state machine. Two parallel research passes captured Swarm independently; they agree on every substantive point (the client-side/stateless design, the handoff-via-function-return mechanism, the "flexible workflows rather than rigid hierarchies" framing) and no factual contradiction exists between them — the second capture simply goes one layer deeper into implementation (the `Result` object, context-variable threading, and the five-step `client.run()` loop) than the first. The repository's own deprecation notice states plainly that "Swarm is now replaced by the OpenAI Agents SDK, which is a production-ready evolution of Swarm," making Swarm one of the clearest public examples of a major lab explicitly labeling a coordination pattern sound but an implementation not production-ready — the durability, state-management, and hosting gaps were what the Agents SDK was built to close, not the handoff concept itself.

CAMEL reaches peer-to-peer coordination through a narrower mechanism: a fixed two-agent role-play where one LLM plays an "AI user" who issues instructions and the other plays an "AI assistant" who executes them, conversing until the AI user judges the task complete — no manager agent decides turn order. The technique that keeps this dialogue coherent without a controller is **inception prompting**: each agent is primed with prompts framed as if the other agent were speaking first, a "role flip" that the original NeurIPS 2023 paper found sufficient to make the pair reliably guide each other through multi-step tasks using only role-establishing prompts. An upstream **task-specifier agent** elaborates a human's vague initial idea into a concrete task description before the role-play pair begins, reducing the ambiguity that would otherwise derail a two-agent dialogue with no referee. CAMEL is architecturally the minimal-viable counterexample to the assumption that multi-agent systems need a centralized manager to stay coherent, and the project has leaned into that as a research program rather than purely an engineering one — it describes itself as pursuing "the scaling laws of agents," treats generated conversational data as a first-class research artifact (producing named datasets like CAMEL AI Society, CAMEL Code, CAMEL Math, and CAMEL Science), and states four architectural pillars — Evolvability, Scalability (claiming support for up to 1M agents), Statefulness, and "Code-as-Prompt" (the principle that every line of code and comment doubles as a prompt for the agents that consume it).

## Conversation-driven with configurable topology: AutoGen / AG2

AutoGen occupies a middle position between pure peer-to-peer dialogue and a fixed pipeline: individual exchanges are conversational turns, but many deployments layer a coordinating agent on top to keep group conversations coherent, and the framework explicitly supports moving between both modes at runtime. Its foundational abstraction is `ConversableAgent` — a generic base class for any participant, human or machine, that can send and receive messages — built on the idea that agents are simultaneously **conversable** (message-passing is the universal interface) and **customizable** (the same base class can be backed by an LLM, a human, or a tool/code executor). Two concrete subclasses matter most: `AssistantAgent`, an LLM-backed role that generates a solution (typically code) and refines it based on execution feedback; and `UserProxyAgent`, which represents the human/environment and whose `human_input_mode` setting is the main lever for how autonomous versus supervised a run is — it can solicit a human at every turn, auto-execute code blocks it detects, or, given an `llm_config`, generate its own LLM responses instead of forwarding to a person. Code execution is typically sandboxed (e.g., in Docker) with stdout/stderr/exceptions fed back into the message stream, giving the `AssistantAgent` real execution feedback rather than static self-review — the same "give the agent a feedback loop from real execution" pattern also appears in [MetaGPT](#assembly-line-fixed-role-pipelines-metagpt-and-chatdev) and ChatDev below. Beyond raw two-agent chat, AutoGen supports **dynamic group topologies**: registered auto-reply functions for ad hoc hierarchical structures, a **GroupChat** pattern where a manager agent dynamically selects which peer speaks next, and LLM-driven function calls that decide at runtime which agents should join the conversation — a lightweight centralized dispatcher sitting above what is otherwise a flat pool of peers.

AutoGen is also a case study in how a framework's community and its original steward can diverge architecturally. It originated at Microsoft Research in Fall 2023 (a Microsoft/Penn State/University of Washington collaboration); in late 2024 its original creators, Chi Wang and Qingyun Wu, left Microsoft and forked the project into **AG2**, a community-governed continuation that deliberately preserves the 0.2-era `ConversableAgent` architecture for stability. Microsoft's own line diverged sharply into **AutoGen 0.4**, a full rewrite onto an actor-model, layered design aimed at distributed, event-driven, cross-language enterprise systems — meaning "AutoGen" today names two architecturally different things depending on which lineage is meant, an important disambiguation when citing it. That Microsoft-side lineage did not stop at 0.4: as of 2026, Microsoft has folded both AutoGen and its separate Semantic Kernel framework into a single successor, **Microsoft Agent Framework**, which the official Microsoft Learn overview describes as "the direct successor, created by the same teams," combining "AutoGen's simple abstractions for single- and multi-agent patterns with Semantic Kernel's enterprise-grade features such as session-based state management, type safety, filters, telemetry, and extensive model and embedding support," and adding graph-based **Workflows** for explicit, type-safe, checkpointed multi-agent execution paths on top of conversational agents. Microsoft shipped a 1.0 release of Agent Framework in early 2026 and continues to support Semantic Kernel 1.x, but positions Agent Framework as the default choice for new Microsoft-ecosystem agent projects — closing the loop on the fork story: two divergent Microsoft-adjacent lineages (AG2's community-preserved 0.2 API and Microsoft's actor-model 0.4 rewrite) now both point at the same downstream consolidation.

## Role-based crews, autonomous or deterministic: CrewAI

CrewAI is distinctive for treating agent autonomy as a dial rather than a fixed commitment: its documentation frames the whole framework around two complementary primitives, **Crews** (teams of agents collaborating autonomously through role-based decision-making) and **Flows** (production-ready, event-driven workflows with explicit start/listen/router steps, state management, persistence, and the ability to resume long-running executions). The existence of both in one framework is itself a design statement — pure autonomous role-play is good for open-ended collaborative reasoning, but CrewAI treats deterministic control flow around and between the autonomous parts as a first-class production need rather than an afterthought. Agents are defined with a **role, goal, and backstory** — the backstory in particular is a distinguishing persona-priming mechanism, giving the LLM narrative context about who it is meant to be on the theory that persona framing shapes output quality more than bare instructions alone (a philosophy that parallels ChatDev's per-phase title assignments below, though CrewAI's backstories are written once per agent rather than reassigned per phase). A `Crew` is instantiated with `agents`, `tasks`, and a `process`, which can be **sequential** (a linear pipeline where each task can reference prior outputs) or **hierarchical** (a manager agent, requiring a configured `manager_llm`, delegates to and validates member agents — an explicit centralized-orchestrator variant layered on the same flat agent pool, structurally analogous to AutoGen's GroupChat manager). Fine-grained observability comes from step, task, and before/after-kickoff callbacks, and memory spans short-term, long-term, and entity scopes. CrewAI's documentation also explicitly references support for both MCP (tool access) and A2A (cross-framework agent communication) — positioning the framework as interoperable with the emerging protocol layer discussed below rather than a closed ecosystem, alongside enterprise integrations and access-control features aimed at production teams.

## Assembly-line, fixed-role pipelines: MetaGPT and ChatDev

MetaGPT and ChatDev both simulate a software company with fixed roles handing structured artifacts down a pipeline, in direct architectural contrast to the conversational and role-play models above — the shared thesis is that giving agents *process discipline* scales collaboration better than giving agents *more freedom to converse*.

MetaGPT's tagline, "Code = SOP(Team)," materializes **Standardized Operating Procedures** — the codified workflows real engineering organizations use — directly into the prompt sequences given to a five-role team: **Product Manager, Architect, Project Manager, Engineer, and QA Engineer**, each with a narrowly defined responsibility handing structured artifacts to the next role. The motivating problem is that naively chaining LLMs produces "logic inconsistencies due to cascading hallucinations" with no built-in mechanism to catch errors; SOPs let agents with human-like domain expertise verify each other's intermediate outputs before they propagate further down the pipeline. A single line of natural-language requirement expands, through the role pipeline, into user stories, competitive analysis, formal requirements, data structure definitions, and API specifications before any code is written — a deliberate front-loading of design mirroring waterfall discipline. Like AutoGen's Docker-sandboxed execution feedback, MetaGPT includes an **executable feedback mechanism** where generated code is actually run and errors/test failures are fed back to debug and refine it; the paper reports this produced a 5.4% absolute improvement on the MBPP benchmark and state-of-the-art results on both HumanEval and MBPP at time of publication (ICLR 2024 oral, ranked #1 in the LLM-agent category). MetaGPT's fixed five-role pipeline is also the most frequently used *baseline* in later work testing whether permanently-assigned roles are actually the right design: the [static-vs-dynamic-roles synthesis](../syntheses/static-vs-dynamic-roles-multi-agent-success.md) finds two independent papers (AgentNet, LATTE) benchmarking directly against MetaGPT and both showing dynamic/adaptive role allocation matching or substantially beating it.

ChatDev models itself as a "virtual, chat-powered software development company" following the same waterfall shape — **designing → coding → testing → documenting** — but its distinguishing mechanism is *how* it structures conversations within each phase rather than just the phase sequence itself. Each phase is decomposed into a **chat chain**: a sequence of atomic, two-agent exchanges, each targeting one narrow subgoal, with outcomes propagating sequentially so a phase's result is the accumulated product of many small, targeted dialogues rather than one large unconstrained generation. Every chat within a chain is a **duo-role** exchange between an **Instructor** (initiates and directs the sub-task) and an **Assistant** (executes it), continuing until both sides converge on a matching structured message signaling agreement — giving each atomic exchange a clear, checkable termination condition rather than an open-ended stopping heuristic. Agents adopt different organizational titles per phase (CEO/CTO/CPO for designing; CTO/Programmer/Designer for coding; Programmer/Reviewer/Tester for testing; CEO/CPO/CTO/Programmer for documenting), with the same underlying agent shifting identities across phases rather than being permanently bound to one role — a lighter-weight variant of MetaGPT's fixed five-role cast. ChatDev's paper frames a bundle of "communicative dehallucination" mechanisms as its central contribution, going beyond MetaGPT's SOP approach: phase decomposition itself constrains what any single generation step must get right; **cross-examination** structures role pairs to give targeted review rather than passive acceptance; **thought instruction** temporarily swaps which agent plays CTO versus Programmer to force a large task into smaller tractable pieces; and deliberate **memory purging** of earlier code versions prevents the model from anchoring on and repeating prior hallucinated content — a notably simpler memory model than "generative agents"-style retrieval-plus-reflection, which the paper argues is sufficient specifically because the chain's sequential structure already makes relevant prior information locally accessible. Across 70 generated software tasks, ChatDev reported averaging 17.04 files and 131.61 lines per project, $0.2967 in LLM API cost, and 409.84 seconds of development time, while acknowledging non-deterministic output even at low temperature, occasional UX misalignment, and no direct empirical comparison against contemporaries like GPT-Engineer or MetaGPT in the original evaluation.

## Cross-vendor interoperability at the protocol level: Google's A2A

Every framework above solves coordination *within* one framework's process boundary; Google's **Agent2Agent (A2A) protocol**, announced April 9, 2025 and now governed by the Linux Foundation under Apache-2.0 licensing, solves a different problem — how agents built by *different* vendors, on *different* frameworks, inside *different* organizations discover each other, exchange messages, and coordinate multi-step tasks across trust boundaries none of the frameworks above were designed to cross. It launched with more than 50 technology partners (including Atlassian, Box, Cohere, LangChain, MongoDB, PayPal, Salesforce, SAP, and ServiceNow) plus major systems integrators and observability vendors, signaling an intent to be a neutral standard rather than a Google-controlled API — and CrewAI's documented A2A support above is a concrete instance of a framework opting into that standard rather than building its own bespoke cross-framework bridge. A2A's core objects are **Agent Cards** (JSON documents an agent publishes to advertise its capabilities, analogous to an OpenAPI spec but for agent capabilities rather than REST endpoints, letting a client agent discover and select a remote agent to hand work to), **Tasks** (the central unit of work, with an explicit lifecycle supporting both immediate completion and long-running execution with streamed status updates), **Artifacts** (the outputs handed back from remote agent to client agent on Task completion), and **Messages** composed of typed "parts" (text, images, etc.) that enable format negotiation between agents supporting different modalities. Transport is JSON-RPC 2.0 over HTTP/HTTPS with Server-Sent Events layered on for streaming — a deliberately language-agnostic choice — secured with TLS, OAuth 2.0 for mutual agent authentication, and JWTs for scoped authorization tokens. The announcement is explicit that A2A is **complementary to, not competing with, the Model Context Protocol (MCP)**: MCP addresses how a single agent gets useful tools and context, while A2A addresses how multiple independent agents discover, message, and coordinate with each other at scale — together framed as a full interoperability stack, MCP for agent-to-tool and A2A for agent-to-agent. This positions A2A as orthogonal to every architectural philosophy above rather than a competing alternative to them: a CrewAI hierarchical crew, an AutoGen GroupChat, and a MetaGPT pipeline could each, in principle, expose themselves as A2A-addressable remote agents to be composed by external callers that have no visibility into (or need to understand) the internal coordination pattern each framework uses.
