# Pi

Pi (`pi-mono`) is a coding agent Meeseeks has evaluated as an **interchangeable harness** — a candidate replacement for the [Claude Code](claude-code.md) dependency, sitting alongside the [LangChain ecosystem](langchain-ecosystem.md) as one of three integration targets. Like Claude Code and unlike LangChain, it is a self-contained CLI process an orchestrator spawns and drives over stdio; unlike Claude Code, it exposes a structured bidirectional control protocol rather than a PTY-plus-hooks surface. This page frames Pi as a system and routes to its internals and the comparative analyses; the substance of whether Meeseeks should adopt it lives in the [Claude Code vs. Pi runtime comparison](../syntheses/claude-vs-pi-runtime-interfaces.md).

## Shape of the codebase

Pi is a Node.js runtime spanning over 8,000 semantic units across three core packages: `agent` (the dependency-light turn engine), `AI` (provider abstraction), and `coding-agent` (the CLI, modes, sessions, and extensions). The architectural centre is a strict split between a **stateless functional loop** and a **stateful orchestrating class**, documented in depth as the [Pi agentic loop](../concepts/pi-agentic-loop.md) and read as a set of reusable design decisions in the [Pi agentic loop design patterns](../syntheses/pi-agentic-loop-design-patterns.md) synthesis.

## Four invocation modes

`resolveAppMode` (`packages/coding-agent/src/main.ts`) selects one of four modes, and which one an orchestrator picks determines the entire integration surface:

- **Interactive** — a full TUI via the ProcessTerminal framework; rich terminal rendering suitable for console panels, but no structured events and no programmatic control.
- **Print** — plain text on stdout with a 0/1 exit code; one-shot, non-interactive.
- **JSON** — LF-delimited JSON events on stdout; structured output, one direction.
- **RPC** — JSON-L over stdin/stdout, bidirectional, with 30+ typed commands (`RpcCommand` in `packages/coding-agent/src/modes/rpc/rpc-types.ts`) covering prompting, steering, model selection (`set_model`, `cycle_model`, `get_available_models`), and session control.

The [runtime comparison](../syntheses/claude-vs-pi-runtime-interfaces.md) works through the consequence for Meeseeks: the RPC mode is the richest control surface of any candidate harness, but it produces JSON-L rather than ANSI, so an adapter would have to synthesize terminal output from structured events — the same rendering trade-off the [LangChain frontend rendering](../concepts/langchain-frontend-rendering.md) analysis reaches from the other side. Interactive and RPC are mutually exclusive: Pi offers a TUI *or* structured control, never both at once.

## Memory and skills

*Added 2026-07-26, closing a gap this page previously left open — its coverage came from a code-rag pass scoped to the agentic loop and RPC surface, and said nothing about instructions, skills, or how learned state persists.*

**Context files.** Pi loads `AGENTS.md` or `CLAUDE.md` (either name) from `~/.pi/agent/AGENTS.md` (global), every parent directory walking up from the working directory, and the current directory. **All matching files are concatenated** — the same additive-layering semantics [Claude Code uses](claude-code.md#capability-surface), not the override-wins precedence [`dcode`](deep-agents-code.md) applies to its skill roots. Loading is disabled wholesale with `--no-context-files`/`-nc`; there is no per-file exclude list comparable to Claude Code's `claudeMdExcludes`. Reading either filename is a deliberate interoperability choice — Pi is the only one of the three agents that natively reads *both* conventions rather than picking one and requiring an import or symlink for the other.

**Skills** are Pi's only progressive-disclosure mechanism, and it explicitly implements the [Agent Skills specification](https://agentskills.io/specification) — the same open standard [Deep Agents](deep-agents.md) and [Claude Code](claude-code.md#capability-surface) use, making skills the one context primitive where all three coding agents converge on shared markup. The mechanism is stated plainly in Pi's own docs: at startup Pi scans skill locations and extracts only names and descriptions, embedding them in the system prompt in XML per the spec; the agent then uses its `read` tool to load the full `SKILL.md` when a task matches. Pi's docs name this outright as "progressive disclosure: only descriptions are always in context, full instructions load on-demand" — the same formula this wiki's [context-engineering synthesis](../syntheses/context-economics.md) derives independently from Deep Agents.

Two details differ from the other two agents' skill handling:

- **Six discovery roots**, more granular than either alternative: global `~/.pi/agent/skills/` and `~/.agents/skills/`; project `.pi/skills/` and `.agents/skills/` (searched from cwd up to the git root or filesystem root, and gated on the project being *trusted* first); package-distributed skills via a `skills/` directory or a `pi.skills` entry in `package.json`; a `skills` array in settings; and repeatable `--skill <path>` CLI flags, which stay additive even alongside `--no-skills`. The package-distribution channel (`pi.skills` in `package.json`) has no analog in Claude Code or `dcode` — it piggybacks on the Node ecosystem's existing dependency-distribution mechanism rather than inventing a plugin/marketplace layer the way `dcode` does.
- **A deliberate, named spec deviation.** Pi does not require a skill's `name` to match its parent directory, calling the standard's requirement "suboptimal for shared skill directories used across multiple agent harnesses" — a design choice aimed squarely at the cross-CLI-sharing use case this wiki's skills coverage keeps circling back to.

Frontmatter matches the spec closely: `name` (required, ≤64 chars), `description` (required, ≤1024 chars), plus optional `license`, `compatibility`, `metadata`, an experimental `allowed-tools`, and `disable-model-invocation` (hides the skill from the system prompt; invoke only via `/skill:name`). This is a narrower field set than Claude Code's skills frontmatter, which adds `user-invocable`, `context: fork` for subagent execution, scoped `hooks`, and `paths` for glob-gated auto-activation — Pi has no equivalent of that last field, so its skills cannot be conditioned on which files are in play, only on the model's judgment of the description.

**No dedicated learned-memory system.** This is the sharpest contrast with the other two agents. Neither Claude Code's auto memory (`~/.claude/projects/<project>/memory/`, agent-written, index-plus-topic-files) nor `dcode`'s `memories/` directory has a Pi counterpart. Pi's own design docs make this an explicit architectural stance rather than an oversight: *"treat session as all durable agent state, not just transcript history... that suggests continuing with one durable session log rather than adding harness sidecars."* Model changes, thinking-level changes, active-tool changes, compactions, and branch summaries all live in the one JSONL session log rather than in a separate memory file the agent maintains across sessions. The tradeoff is direct: Claude Code and `dcode` let an agent accumulate cross-session knowledge that survives starting a fresh conversation; Pi's equivalent state is bound to a specific session unless a user explicitly forks or resumes it. Whatever an agent "learned" persists only as long as that session thread does.

## Control seams, permissions, and sessions

Pi's programmability is **in-process**: the agentic loop is studded with JavaScript callbacks (`transformContext`, `getApiKey`, `convertToLlm`, the steering/follow-up queues, `beforeToolCall`/`afterToolCall`) rather than the external shell hooks Claude Code fires. That is precisely the gap that complicates external orchestration — there is no `curl`-to-the-server equivalent to signal lifecycle state, so a supervisor must either monitor the RPC event stream or extend Pi with a notification mechanism it does not ship. Tool permissions are coarse — global `--tools`/`--no-tools` with no per-operation gating, filesystem scoping, or OS sandboxing, in contrast to Claude Code's allow/deny rules and [bubblewrap/Seatbelt sandboxing](../runbooks/claude-code-sandboxing.md). Sessions are handled by a `SessionManager` storing versioned JSONL sessions with new/resume/fork/import navigation managed by `AgentSessionRuntime`. Sessions auto-save to `~/.pi/agent/sessions/` organized by working directory and are addressable by path or partial UUID (`--session`, `--fork`); `--no-session` opts out for ephemeral runs. `/tree` navigates the tree, `/fork` branches from a past message, `/clone` duplicates the active branch, and `/export`/`/share` push a session out as HTML — `/share` specifically as a private GitHub gist with a shareable link, a sharing mechanism neither Claude Code nor `dcode` documents. This page previously claimed Claude Code "exposes no session persistence at all"; that was **wrong**, and a 2026-07-25 review against the live docs corrected it — Claude Code ships `/resume`, `/branch`, `/fork`, `/background`, and `/rewind` (which rolls back *code and conversation* to a checkpoint), so the two are broadly at parity here rather than Pi holding an advantage. Pi's edge on this axis is narrower than stated: JSONL sessions are inspectable files an external process can read, whereas Claude Code's are addressable only through its own commands.
